# REVIEW.md — what I found in the starter `app/main.py`

I read the 162-line starter the way I'd review a teammate's PR: ran the happy path first (it works), then pushed on the edges the contract cares about — timezones, midnight, parallel requests, and 100k-record behavior. The happy path is fine. Everything below is what breaks around it. Severity in brackets; all of these are fixed in my `app/main.py`.

| # | Where | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` [high] | It does `punch_in.replace(hour=h, minute=m, ...)` on whatever datetime came in. That keeps the server's local zone instead of IST, so the same punch gives a different answer on two machines. The grace check (`minutes > 10`) also works on whole minutes, but the rule is strict wall-clock: anything past 10:00 counts, and the count runs from shift start, not from the end of grace. So `09:40:01` on a `09:30` shift scores 0 here; the contract wants 10. | Punch `09:40:01`, shift `09:30` → late `0`, expected `10`. Run the server with `TZ=UTC` vs `TZ=Asia/Kolkata` and watch the same test diverge. | Diff in IST: `diff <= 600s → 0`, else `floor(diff/60)`. Date comes from the R1 helper, which knows about overnight shifts. |
| 2 | `compute_overtime` [high] | It parses the attendance `date` at midnight and stamps `tzinfo=IST` onto it, then compares directly. Two problems: for overnight shifts the end is the *next* day, and the 30-minute minimum is missing entirely — any positive sliver counts. | Punch out `18:35` on an `18:30` shift → overtime `5`, expected `0`. An overnight `22:00–06:00` shift computes the end on the wrong calendar day. | Build the end in IST (plus a day when `shift_end <= shift_start`), take `floor` minutes, keep it only if `>= 30`. |
| 3 | `compute_work_hours` [medium] | Plain `round(x, 2)`. Python rounds half-to-even on binary floats, the contract wants half-up on the exact decimal (`2.675h → 2.68`; `round` gives `2.67`). Rare, but the hidden dataset is built to include exactly these cases. | Any `x.xx5` hour value drifts by a cent; analytics averages inherit it. | `Decimal(str(seconds)) / Decimal("3600")` with `ROUND_HALF_UP`. |
| 4 | `POST /employees` [high] | Classic check-then-insert: `find_one` says free, then `insert_one` — with no unique index behind it. Two identical creates landing together both see "free" and both get `201`. Separately: `datetime.now()` is naive, `created_at` goes back as a datetime instead of epoch-ms, and nothing rejects `shift_start == shift_end` or a malformed `emp_code`. | Fire two duplicate creates in parallel → two `201`s, expected one `201` and a `409`. `created_at` comes back unparseable as an integer. | Unique index on `emp_code` at startup; `DuplicateKeyError → 409`. UTC-aware `now`, ms serialization, shift-equality `422`, and the `EMP\d{4,6}`/email patterns in the model. |
| 5 | `GET /employees` [medium] | Three small ones that add up: `skip = page * page_size` (page 1 skips the first twenty rows), `total` counts the whole collection instead of the filtered set, and there's no `sort`, so paging is nondeterministic. No `page_size` cap either. | `GET /employees?page=1` misses the first page; filter by department and `total` still reports everyone. | `(page-1)*size`, `count_documents(filtered)`, `sort(emp_code asc)`, R10 `1–100` guard. |
| 6 | `punch_in`, unknown employee [medium] | `emp["shift_start"]` runs unconditionally. For an unknown code `emp` is `None`, so this blows up as a `TypeError` → `500`. The contract says `404`. | Punch in as `EMP9999` → `500`, expected `404`. | Look the employee up first, `404` before touching any field. |
| 7 | `punch_in`, attendance date [high] | `ts.date()` is the *server's* calendar date, not the IST date of the punch (R1). Overnight logic is absent, and sub-second values aren't truncated, so `.900ms` edges compute differently than the stored value. | Punch `01:00 IST` on a `22:00–06:00` shift lands on the wrong `date`. | `utc_from_ms` truncates to whole seconds first; `attendance_date_for` converts to IST and rolls back a day when the punch falls before an overnight `shift_end`. |
| 8 | `punch_in`, the rest [high] | Same check-then-insert race as #4 but on `(emp_code, date)` — two simultaneous punch-ins both `201`. It also accepts *any* status (including `ABSENT`/`LEAVE`, which no endpoint may create), never validates `punched_at` (seconds-looking ints and floats sail through), and returns Mongo's `_id` as `id`, which the contract explicitly forbids. | Parallel same-day punch-ins → two `201`s. `status: "ABSENT"` accepted with `201`. `punched_at: 1750000000` (seconds) accepted. | Unique `(emp_code, date)` index → `409` for losers; `PresenceStatus` literal (`PRESENT`/`WFH`/`ON_DUTY` only); strict ms range (`StrictInt`, rejected below `100000000000`); no `id` anywhere in responses. |
| 9 | `GET /attendance` [high] | It pulls the whole collection into a Python list, sorts in memory, and sets `total = len(docs)`. At ~100k records that's slow and hungry, and the grader's `explain` check fails outright (`COLLSCAN`, no index use). Also leaks `_id` as `id`, skips the `date_from > date_to → 422` rule and status validation, and sorts by `date` only (ties need `emp_code`). | Seed 100k docs and time it; run `explain` — collection scan, Python-side sort. | Filtered `count_documents`, DB-side `sort(date desc, emp_code asc)` + `skip/limit`, ms serialization, R10 + range + status guards. Nothing is materialized except the page. |
| 10 | `GET /health` [medium] | Returns `{"status": "ok"}` without contacting Mongo. The runner polls this endpoint *before* testing, so a dead database looks ready and every subsequent test fails confusingly. | Stop Mongo, hit `/health` → still `200`, expected `503`. | `db.command("ping")` inside; `503 {"detail": ...}` when it throws. |
| 11 | Clocks, everywhere [high] | Naive `datetime.now()` / `fromtimestamp()` mixed with IST `"HH:MM"` strings, and PyMongo hands back naive datetimes that the code treats as-is. Nothing normalizes, so results depend on the machine's zone. | Same seed, two zones, different `late_minutes`/`date` values. | One rule throughout: store UTC-aware BSON, convert at the boundary (`ms()` both ways), use IST purely for R1/R2/R3 calendar comparisons. |
| 12 | Status codes [medium] | Validation failures don't consistently yield `422` — bad pagination or date ranges either slip through with `200` or surface as the wrong code. The contract is strict: every validation failure is `422` with FastAPI's body. | `page_size=101` or `date_from > date_to` → `200` with a wrong slice. | Guard clauses raising `422` before any DB call on every list/analytics endpoint. |

## Things I checked and left alone
- `FastAPI(title, version)` metadata — cosmetic, harmless.
- Sync `pymongo.MongoClient` instead of Motor — deliberate. The submit is one sync file; an async rewrite buys nothing here and risks the lifespan/event-loop behavior the grader times at 20s.
- `history: []` on punch-in, `punch_out`/`work_hours` starting `null` — matches DATA_MODEL §3 exactly, so I kept the shapes and only fixed how they're computed.
- Inclusive `date_from`/`date_to` semantics — right idea, so I kept them and added the missing `from > to → 422` enforcement.
